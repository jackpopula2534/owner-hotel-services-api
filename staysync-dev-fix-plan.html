1 Phase 1 — Critical (Hotfix ทันที)

เป้าหมาย: อุดช่องโหว่ที่ทำให้เสียเงิน/ผิดกฎหมายโดยตรง

🔐 ความปลอดภัยการชำระเงิน + ความครบถ้วน PDPA
CRITICAL สัปดาห์ที่ 1

รวมงาน 3 ก้อน — ทำคู่กับ regression test ของ payment flow เพื่อกัน side-effect

PromptPay webhook เปิด public + ไม่ verify signature

SALES-01
Critical
promptpay.controller.ts:52 (@Public) · promptpay.service.ts:265 handleWebhook()

ปัญหา: endpoint POST /promptpay/webhook ติด @Public() และไม่ตรวจลายเซ็น — ผู้โจมตียิง transactionRef + status:paid ปลอม เพื่อ mark invoice เป็นจ่ายแล้วและเปิด subscription ฟรีได้ (กันแค่ status !== 'pending' ซึ่งไม่พอ)

แก้: เพิ่ม HMAC-SHA256 signature verification (ดึง secret จาก ConfigService), reject ถ้า signature ไม่ผ่าน, และใช้ conditional update (where:{status:'pending'}) กัน race

Effort: Mเจ้าของ: Backend/PaymentsTest: replay + fake-signature spec

TrueMoney/2C2P callback ไม่ verify hash

SALES-02
Critical
truemoney.service.ts:109 handleCallback() · truemoney.controller.ts:32

ปัญหา: เชื่อ dto.respCode === '0000' ตรงๆ ไม่ตรวจ JWT/hash จาก gateway (คอมเมนต์บอก "ตรวจ hash" แต่โค้ดไม่ได้ทำ) + guard ของ route /callback ไม่สอดคล้องกับ route อื่น

แก้: verify ลายเซ็น JWT/HMAC ของ callback ด้วย secretKey ก่อน mark paid, จัด guard ให้ชัด (public แต่ verified)

Effort: Mเจ้าของ: Backend/PaymentsTest: forged-callback rejection

Right to Erasure ลบไม่ครบ — PII ตกค้างในตาราง Booking

LEGAL-01
Critical
schema.prisma:288-291 (Booking) · data-export.processor.ts:252 anonymizeTenantGuests()

ปัญหา: ตาราง Booking เก็บ guestFirstName/LastName/Email/Phone ซ้ำ แต่ฟังก์ชัน erasure anonymize เฉพาะตาราง guest และ employee → หลังลบ ชื่อ/อีเมล/เบอร์ลูกค้ายังอยู่ใน booking (และอีกจุดที่ schema:425) ผิด PDPA ม.33

แก้: ขยาย erasure ให้ updateMany ฟิลด์ PII ใน booking/related models ด้วย หรือเลิก denormalize แล้ว join จาก guest ตอน query

Effort: Mเจ้าของ: Backend/ComplianceTest: erasure แล้ว assert ไม่เหลือ PII

2 Phase 2 — High (Sprint ถัดไป)

เป้าหมาย: ความถูกต้องของเงิน/ภาษี และความสอดคล้องของข้อมูล

💳 ความถูกต้องการเงิน + ใบกำกับภาษี
HIGH สัปดาห์ที่ 2–3

เน้นป้องกัน payment ซ้ำ และทำให้ใบแจ้งหนี้ถูกต้องตามภาษีไทย

Stripe webhook ไม่มี idempotency → payment ซ้ำ

SALES-03
High
stripe.service.ts:175 onPaymentIntentSucceeded() (signature ตรวจถูกต้องแล้ว ✓)

ปัญหา: payments.create() โดยไม่เช็คว่ามี payment สำเร็จอยู่แล้ว — Stripe retry webhook = payment ซ้ำ + invoice ถูก mark paid ซ้ำ

แก้: ก่อน create เช็ค findFirst({invoice_id, status:'approved'}) แล้ว return เป็น no-op ถ้ามีแล้ว (idempotent)

Effort: Sเจ้าของ: Backend/PaymentsTest: duplicate webhook → 1 payment

approvePayment ไม่กันกดซ้ำ + side-effects ไม่อยู่ใน transaction

SALES-04
High
payments.service.ts:104 approvePayment()

ปัญหา: ไม่เช็คว่า approve ไปแล้ว และ side-effects (invoice/subscription/booking) รันใน .catch() แยกกัน ไม่ห่อ $transaction → กด approve 2 ครั้ง = ต่ออายุ subscription ซ้ำ; พังกลางทาง = ข้อมูลไม่สอดคล้อง

แก้: guard if(status==='approved') throw, ห่อทั้ง flow ใน prisma.$transaction()

Effort: Mเจ้าของ: Backend/PaymentsTest: double-approve idempotent

ใบแจ้งหนี้ SaaS ไม่มี VAT (ผิดข้อกำหนดใบกำกับภาษี)

LEGAL-02
High
invoices.service.ts:10 create() · schema.prisma:1151 (มีแค่ field amount)

ปัญหา: ใบแจ้งหนี้ค่า subscription เก็บแค่ amount ไม่มี subtotal/vat_rate/vat_amount — ออกใบกำกับภาษีเต็มรูปไม่ได้ (หมายเหตุ: ฝั่ง AR ของโรงแรมใน modules/accounts-receivable มี VAT แล้ว ขาดเฉพาะบิล SaaS)

แก้: เพิ่มฟิลด์ subtotal/vat_rate/vat_amount + คำนวณ VAT 7% ตอนสร้าง, แสดงบนใบกำกับ

Effort: Mเจ้าของ: Backend/Billingต้อง migration

ใบกำกับ AR: ไม่บังคับ seller/buyer tax ID + ไม่มี gap-detection เลขรัน

LEGAL-03
High
modules/accounts-receivable/ar-invoices/ar-invoices.service.ts · document-settings

ปัญหา: ออกใบกำกับได้โดยไม่มี seller tax ID; B2B (City Ledger) ไม่บังคับ buyer tax ID; เลขรันใบกำกับไม่มี audit ตรวจเลขขาด/ซ้ำ (กรมสรรพากรต้องเรียงต่อเนื่องไม่มีช่อง)

แก้: validate settings.taxId ก่อน issue + denormalize ลงใบกำกับ; เพิ่ม DocumentSequenceAudit log ทุกครั้งที่เดินเลข (issue/void)

Effort: Lเจ้าของ: Backend/Accounting

3 Phase 3 — Medium & Hardening

เป้าหมาย: ปิดช่อง race condition, เสริมหลักฐานความยินยอม และทำ audit log ให้ tamper-evident

🧩 Robustness & Compliance Hardening
MEDIUM สัปดาห์ที่ 4+

ทำหลังจาก Critical/High เสร็จ — ไม่บล็อก go-live แต่ลดความเสี่ยงระยะยาว

Coupon redeem race condition (TOCTOU)

SALES-05
Medium
coupons.service.ts:388 (เช็ค limit) vs :439 ($transaction)

ปัญหา: เช็ค limit ต่อ tenant อยู่นอก transaction → 2 request พร้อมกันผ่านได้ทั้งคู่ (มี unique constraint กันบางส่วน)

แก้: ย้ายการนับ/เช็ค limit เข้าไปใน $transaction เดียวกับการสร้าง redemption

Effort: Sเจ้าของ: Backend/Billing

ไม่บันทึก consent IP address

LEGAL-04
Medium
guests.service.ts:150 · create-guest.dto.ts (ไม่มี field IP)

ปัญหา: คอมเมนต์บอกเก็บ IP แต่เขียนจริงแค่ consentGiven/consentAt/consentVersion — พิสูจน์การให้ความยินยอม ณ เวลา/ที่มาไม่ได้

แก้: ดึง IP จาก request (req.ip/X-Forwarded-For) เขียนลง consentIpAddress; ทำให้ employee onboarding ด้วย

Effort: Sเจ้าของ: Backend/Compliance

Audit log ยังไม่ tamper-evident + ไม่มี cron retention

LEGAL-05
Medium
schema.prisma (AuditLog) · common/services/data-retention.service.ts

ปัญหา: audit log แก้ไข/ลบได้ (ไม่มี hash chain) และ retention policy ของ audit log (3 ปี) ประกาศไว้แต่ไม่มี cron ลบจริง (ลบแค่ guests/employees)

แก้: เพิ่ม hash (SHA256 ของ record ก่อนหน้า+ปัจจุบัน) ทำ hash chain; เพิ่ม @Cron purge audit log ตาม policy

Effort: Mเจ้าของ: Backend/Compliance
